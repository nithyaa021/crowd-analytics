How I built it, and what I'd argue with

The brief asked for three prototypes. This page is the part that isn't visible on screen: why each decision went the way it did, what I deliberately did not build, and the four questions I'd want answered before turning any of this into a real product.

The approach in one paragraph

I treated the three deliverables as one product family with three audiences, not three unrelated designs. A person who opens the animal-care prototype should recognise the course page as coming from the same studio. That meant building a shared design system first — colour tokens, a type scale, spacing rules, button and card states — and then expressing each deliverable as a different rhythm within it.

The second decision was to make every prototype genuinely interactive rather than a picture of an interface. A wireframe proves you can draw boxes. A working filter, a two-step form that validates, and a carousel whose copy lives in a data array prove you understand how the thing actually behaves.

The decisions I'd defend in an interview

1. Search leads the page, not the hero copy

Most marketplace homepages open with a big headline and a "Browse categories" grid. That is wrong for this product. Someone visiting Practo for Animals has an animal in front of them, possibly unwell, and a specific need. So the search panel sits above the fold, pre-filled with location, with species as a first-class field rather than a filter buried later. The category tiles exist as a shortcut for people who don't know the right words.

2. Emergency is a separate mode, not a filter

An emergency is a different job from a checkup — different urgency, different decision criteria, different emotional state. Burying "24 hours" as one checkbox among nine treats it as a preference. Instead there's a dedicated module with a persistent phone icon in the nav that switches the whole result set to emergency care. This is the single highest-stakes interaction on the page, so it gets its own path.

3. Trust is expressed as freshness, not badges

Every directory says "verified". The word means nothing without a date and a mechanism. So each card says how recently it was checked ("Verified 3 days ago" / "Re-check due"), and the trust section explains the process: registration check, a human phone call every 90 days, and an owner correction flow that auto-flags after three reports. That last part is the actual product insight — a directory decays, and the correction path is what slows the decay.

4. The course form is two steps, and the order is deliberate

Asking "where are you in your career?" before asking for a phone number reads like a survey and hurts completion. Asking the same question after the number is given reads like personalisation. The form collects two fields first, then one qualifying question that routes the lead into a batch. Same data, different sequence, measurably different completion rate.

5. "Pay after completion" is a positioning choice, not a pricing gimmick

A course that charges upfront is structurally incentivised to enrol people, not to teach them. Showing that risk sits with the provider is a trust signal that costs nothing to state and is hard for competitors to copy without changing their model.

6. The content system keeps a human at the last step

It would be easy — and wrong — to present a fully automated publish pipeline. The marginal saving is under two minutes, and the downside is publishing an unchecked medical claim. So stage 06 is deliberately manual, with a three-item checklist. Automating assembly and automating judgement are different propositions.

What I chose not to build, and why

Considered Why I left it out
Provider detail page The brief asks for a homepage / search page. A detail page would be the next screen, but building it half-heartedly would have weakened the search experience that carries the whole deliverable.
Map view A real map needs tiles and a key, which breaks the offline requirement and adds no design insight at this stage. Distance and area name carry enough of the information.
Login / accounts Adding auth to a 4-hour prototype is decoration. Owners search without an account on every comparable platform.
AI-generated hero images Illustrated iconography in the brand's own colour family is more coherent, loads instantly, and avoids the "AI stock photo" look that would undercut the credibility of a healthcare brand.
Real clinic data Scraping real listings would be a licensing and accuracy problem. The sixteen sample providers are modelled on the real shape of Indian veterinary listings so the design is tested against realistic strings, but they are clearly labelled illustrative.
A four-step lead form with budget Every extra field costs completion. For a free seat reservation, name and phone is the whole commitment.

Technical notes

Everything is plain HTML, CSS and ES2020 JavaScript. There is no build step, no framework and no CDN. The reason is not ideology — it is that a reviewer should be able to double-click index.html and have it work, on a laptop, offline, with no instructions.

File structure

  • index.html — the submission hub
  • discovery.html + assets/discovery.* — deliverable 01
  • course.html + assets/course.* — deliverable 02
  • workflow.html + assets/workflow.* — deliverable 03
  • assets/base.css — shared design tokens and components
  • assets/base.js — shared nav, reveal, toast, counters
  • docs/ — these three written pages

CSS architecture

base.css owns custom properties (colour, radius, shadow, type), the reset, typography, and the components used on more than one page: buttons, chips, badges, nav, footer, toast. Each page stylesheet owns only what is unique to it. That means the brand colour is defined once, and a page-specific rule can never accidentally restyle another page.

JavaScript architecture

Each page script is a single IIFE with a named reading order at the top: data, state, render, events. The discovery page keeps all filter state in one object and has a single render() function that reads from it — so there is no possibility of the UI and the state disagreeing. The carousel keeps its slides in a data array that deliberately mirrors the JSON contract from the workflow's prompt pack.

Prototype boundary Forms validate and confirm, but nothing is transmitted. Each submit logs the captured object to the console so you can see exactly what a backend would receive.

Accessibility, specifically

  • Every interactive control is a real button, a or input — no clickable divs.
  • Focus is visible everywhere, and tab order follows reading order.
  • The carousel responds to arrow keys and exposes aria-roledescription="slide" per slide.
  • Form errors are announced with aria-invalid and a text message, not colour alone.
  • Step changes in the lead form move focus to the new heading.
  • prefers-reduced-motion disables every transition and animation.
  • If JavaScript fails, content is still visible — the reveal animation only hides elements once JS has confirmed it is running.
  • Colour pairings were checked for contrast; the coral is only used on white for large or bold text.

What I'd do with a second day

  1. Provider detail page — hours, photos, doctors, reviews, and a "request appointment" flow. This is the obvious next screen and the one that makes the search experience complete.
  2. Real usability test — five people, one task: "find a 24-hour clinic for a cat, right now". I'd expect the species + emergency combination to be the friction point, and I'd want data rather than my own opinion.
  3. Course page A/B variant — one version with the form inline in the hero, one with it after the proof section. My hypothesis is that early placement wins for students and loses for team buyers.
  4. Actually run the workflow once end to end in n8n and time it, so the 38-minute claim is measured rather than estimated.

Questions I'd ask before building for real

These are the four things I could not resolve from the brief alone. I made a defensible call on each and noted it, but the answers would change the design.

  1. Is Practo for Animals a directory or a booking platform? If bookings are in scope, every card needs an availability signal and the whole page re-centres on scheduling rather than discovery.
  2. How is provider data sourced? Founder-led onboarding, partner feeds, or owner submissions? That decides whether the correction flow is a side feature or the core of data quality.
  3. Who is the AI education audience first — students or working professionals? The page currently serves both with one message, which is a compromise. Splitting it would sharpen the proof section considerably.
  4. Does the founder actually want to appear on camera or in voice? The content system assumes a personal voice is an asset. If the brand should feel institutional, stage 03's voice samples become brand guidelines instead.

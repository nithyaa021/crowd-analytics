# Step P5 — The real backend: engine thread, SQLite and FastAPI (explained for a beginner)

This note explains every file and function written in step P5, in plain English, with a tiny
number example for each idea. Read it once, then explain it out loud in your own words.

---

## 1. What this step does, in six sentences

1. **`app/db.py`** stores two things in SQLite: the **alert history** and the **head-count
   history**.
2. **`app/engine.py`** runs the video loop in a **background thread**, so the web server never
   waits for YOLO. It publishes the newest frame and a snapshot of the numbers into
   **`SharedState`**.
3. **`app/main.py`** is the FastAPI app: it serves the page, streams video as MJPEG, pushes the
   snapshot over a WebSocket, and answers five JSON endpoints.
4. **`static/index.html`** is a deliberately bare page: an `<img src="/video">` and a `<pre>` that
   prints the WebSocket JSON.
5. **`start.bat`** starts the whole thing on Windows with one double-click.
6. **`scripts/smoke_test.py`** starts the real server and checks all ten behaviours end to end.

Nothing from P1–P4 changed behaviour. P5 only *connects* what already existed.

---

## 2. The shape of the whole system

```
                    ┌──────────────────────────────────────┐
                    │  Engine thread (daemon)              │
   demo_videos/ ──▶ │  video → YOLO → zones → analytics    │
                    │  → SQLite rows + evidence JPEGs      │
                    └───────────────┬──────────────────────┘
                                    │ writes (copies)
                          ┌─────────▼──────────┐
                          │    SharedState     │  one lock
                          │ frame, people,     │
                          │ heat, snapshot     │
                          └─────────┬──────────┘
                                    │ reads (copies)
                    ┌───────────────▼──────────────────────┐
                    │  FastAPI (async, several threads)    │
                    │  /video  /ws  /api/*  /  /evidence   │
                    └──────────────────────────────────────┘
```

**Why this shape:** the engine produces about **8 frames per second**; the server must answer in
**milliseconds**. If a request had to wait for a detection, one slow frame would stall the page.
The two halves never call each other's internals — they only meet at `SharedState`.

## 3. `app/config.py` — what was added

| Setting | Value | Why |
| --- | --- | --- |
| `HEADCOUNT_INTERVAL` | `2.0` | seconds of **video** time between two head-count rows |
| `FPS_WINDOW` | `20` | how many recent frame durations the moving average uses |
| `EVIDENCE_URL_PREFIX` | `"/evidence"` | the URL path the photos are served from |
| `DEFAULT_SOURCE` | `"crowded.mp4"` | the clip the engine starts on |

**Why `HEADCOUNT_INTERVAL` is in *video* seconds:** a 2-second row per analysed frame would write
about 8 rows a second on CPU, which is 2400 rows for a 5-minute clip of almost identical numbers.
Every 2 video seconds gives about 22 rows for a 45-second clip.

## 4. `app/db.py` — SQLite

### 4.1 The two tables

```sql
CREATE TABLE alerts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    zone TEXT NOT NULL,
    source TEXT NOT NULL,
    started_at TEXT NOT NULL,     -- real wall-clock time, ISO-8601 UTC
    video_ts REAL NOT NULL,       -- where in the clip, in seconds
    ended_at TEXT,                -- NULL while the alert is still open
    peak_count INTEGER NOT NULL,
    capacity INTEGER NOT NULL,
    keyframe TEXT                 -- "/evidence/alert_7.jpg"
);

CREATE TABLE headcount (
    ts TEXT NOT NULL,
    zone TEXT NOT NULL,
    count INTEGER NOT NULL
);
```

**Why two different times (`started_at` and `video_ts`):** they answer different questions.
`video_ts` says *"at 31.5 s into the clip"* — useful for checking against the video.
`started_at` says *"at 15:15:08 on 9 November"* — useful for a real history feed. A replay has
both, and throwing either away would lose information.

**Why `ended_at` is nullable:** an open alert is the interesting state. `NULL` means "still
happening right now", which is exactly what the dashboard highlights.

### 4.2 `connect()` — a short-lived connection per call

```python
@contextmanager
def connect(db_path=None):
    path = Path(db_path) if db_path else config.DB_PATH
    path.parent.mkdir(parents=True, exist_ok=True)
    connection = sqlite3.connect(str(path), timeout=10.0)
    connection.row_factory = sqlite3.Row
    try:
        yield connection
        connection.commit()
    finally:
        connection.close()
```

**Why a new connection for every function call:** SQLite connection objects **cannot be shared
between threads**, and this app has the engine thread writing while FastAPI threads read. Sharing
one connection would give `ProgrammingError: SQLite objects created in a thread can only be used
in that same thread`. Opening one per call removes the problem completely.

**Why that is not slow:** opening a local SQLite file is roughly **50–100 microseconds**. A frame
takes about 140 **milliseconds**. The database overhead is under 0.1% of the work.

**Why the context manager:** it commits on success and closes in `finally`, so an exception can
never leak a file handle. On Windows a leaked handle keeps `crowd.db` locked, and the **next**
write fails with "database is locked" — a confusing error far from its cause.

**Why `row_factory = sqlite3.Row`:** rows can then be read by column name (`row["zone"]`) and
converted with `dict(row)`, so the API returns JSON without remembering column positions.

### 4.3 Every query is parameterised

```python
connection.execute(
    "INSERT INTO alerts (zone, source, ...) VALUES (?, ?, ...)",
    (zone, source, ...),
)
```

**Never** `f"... VALUES ('{zone}', ...)"`. Why this matters concretely: the test
`test_a_zone_name_with_a_quote_is_stored_safely` inserts a zone called `Main Zone's door`. With
string formatting that apostrophe would end the SQL string and the statement would break (or, with
a crafted name, do something much worse). With `?` it is just text.

### 4.4 The functions

| Function | What it does | Numeric example |
| --- | --- | --- |
| `init_db()` | creates both tables if missing | second run leaves the 1 existing row alone |
| `insert_alert(...)` | inserts and returns the new id | first alert → id `1` → photo `alert_1.jpg` |
| `end_alert(id, ended_at)` | stamps `ended_at`, keeps the row | alert 1 closes at 14:04:02, peak 9 kept |
| `update_peak(id, count)` | `SET peak_count = MAX(peak_count, ?)` | peak 7, count 5 → stays 7; count 9 → 9 |
| `set_keyframe(id, url)` | attaches the photo URL | `/evidence/alert_1.jpg` |
| `list_alerts(limit)` | newest first, capped | limit 2 of ids 1,2,3 → `[3, 2]` |
| `add_headcount(ts, zone, count)` | appends one sample | `("...T14:00:02", "Main Zone", 7)` |
| `headcount_since(minutes)` | last N minutes, **oldest first** | 10 min at 14:10 keeps rows from 14:00 |
| `utc_now_iso()` | wall-clock timestamp | `2026-11-09T15:15:08.424582+00:00` |

**Why `MAX(peak_count, ?)` in SQL and not read-compare-write in Python:** a single statement
cannot be interrupted between the read and the write, so two writers can never lower a peak that
one of them already raised.

**Why `list_alerts` is newest-first but `headcount_since` is oldest-first:** they feed different
UIs. An alert **feed** shows the latest at the top; a line **chart** plots left to right in time
order. Handing each one already sorted means the browser never sorts.

**Why timestamps are ISO-8601 in UTC:** such strings sort alphabetically in the same order they
sort in time. So `WHERE ts >= ?` and `ORDER BY ts` work as plain text comparison — no date parsing
per row, and no timezone ambiguity.

## 5. `app/engine.py` — the background thread

### 5.1 `SharedState` — the only meeting point

```python
state.set(frame=frame, people=people, heat=heatmap.layer(), snapshot=snapshot)
frame, people, snapshot = state.get()
```

**Why one lock for everything:** the video and the numbers beside it must describe the **same
instant**. With two locks a reader could get a frame from 10.0 s and a snapshot from 10.5 s, and
the boxes on the live picture would not match the counts in the table.

**Why `get()` returns all three at once instead of three getters:** three separate locked calls
could interleave with an engine update between them. One locked block guarantees the triple
belongs together.

**Why copies on the way in *and* out:**

| Direction | Without a copy | Result |
| --- | --- | --- |
| in | engine reuses its decode buffer | the picture changes under the reader |
| out | `render()` draws boxes on it | boxes pile up deeper every frame |

The test `test_frame_and_snapshot_always_match` proves the pair stays consistent: it runs a writer
and a reader thread at the same time and asserts the frame's brightness always equals the
snapshot's `ts`. With separate locks that test fails.

**Why a `deepcopy` for the snapshot:** the snapshot contains a **list of dicts** (the zones). A
shallow copy would share those dicts, so a reader editing one would corrupt the engine's state.

### 5.2 `empty_snapshot(source)` — the contract holds from second zero

```python
{"ts": 0.0, "source": "crowded.mp4", "fps": 0.0, "total_people": 0,
 "peak_people": 0, "zones": [], "alerts_active": 0, "new_alert": None}
```

**Why this exists (a real bug found while testing):** the first run of the end-to-end check crashed
with `KeyError: 'ts'`. The dashboard connects instantly, but YOLO needs a second or two to load,
so `/ws` was sending `{}`. That breaks the contract and would force every client to guard against
missing keys. Now `SharedState` starts with a **valid zeroed snapshot**, so the very first message
is well-formed.

### 5.3 `list_clips()` — the security allow-list

```python
return sorted(path.name for path in config.VIDEO_DIR.glob("*.mp4"))
```

**Why this is the security boundary:** `set_source` accepts a value **only** if it is in this
list, and this list is built from the folder's own contents. So the only accepted values are bare
file names that really exist. `"../../zones.json"` can never appear in it.

The smoke test checks this out loud: `POST /api/source` with `{"name": "../../zones.json"}` must
return **400**, and it does.

### 5.4 `Engine` — the loop

```python
def run(self):
    while True:
        try:
            self._play_clip(self.current_source())
        except Exception as error:
            print(f"[engine] stopped on ...: {error!r}")
            time.sleep(1.0)
```

**Why `while True`:** when the footage ends, replaying is more honest than freezing on the last
frame with a crowd that never moves again.

**Why the `try/except`:** a crashed thread would leave a **permanently frozen dashboard with no
explanation**. Printing and continuing keeps the app alive and says what happened.

**Why the thread is a daemon:** closing the terminal must never leave a hidden process holding a
video file open.

#### `_play_clip(source_name)` — everything that remembers, rebuilt

```python
self.detector.reset()
dwell = DwellTracker()
debouncers = {zone.name: AlertDebouncer(zone.name) for zone in zones}
active_alerts = {}
peak_counts = {}
heatmap = None
```

**Why rebuild on every replay:** track IDs, dwell times, heat and alert state all belong to **one
run through one clip**. Carrying them into the replay would produce dwell times measured partly in
the previous loop, and an alert that was still "active" from a video that already finished.

#### The per-frame pipeline

```
grab/retrieve → resize → detect  → count_by_zone → dwell.update → heatmap.add
             → debouncer.update → (sqlite + evidence) → build snapshot → state.set
```

**Why `grab()` then `retrieve()`:** `grab()` advances one frame without decoding it — cheap. Only
every `STRIDE`-th frame is decoded and analysed, so half the decoding work is skipped while the
tracker still gets a sensible frame sequence.

#### `_open_alert` — making a photo when the id already exists

The order is forced by two facts: the file name is `alert_<id>.jpg` (so the **id** must exist
first), and the row stores the photo path (so the **path** must exist before the row is complete).

```python
alert_id = db.insert_alert(...)          # 1. get the id
keyframe = self._save_evidence(alert_id) # 2. write alert_<id>.jpg
if keyframe: db.set_keyframe(...)        # 3. attach the path
```

**Why insert first and patch second:** if the photo write fails, the alert still exists with a
`NULL` keyframe. A **missing picture is much better than a missing alert** — the number is the
evidence, the photo is a bonus.

**Why `peak_counts` is tracked in memory:** `update_peak` on **every frame** would mean 8 database
connections a second for a value that almost never changes. It is written only when the peak
actually rises from 8 to 9.

#### `_save_evidence` — why draw on a copy

```python
frame, _, _ = self.state.get()   # already a copy
canvas = frame.copy()
```

**Why:** the engine must never paint into the frame that `/video` is streaming, or the alert stamp
and boxes would appear in the live view and accumulate.

#### `measured_fps()` — moving average

```
20 frames in 2.8 s  ->  20 / 2.8 ≈ 7.1 fps
```

**Why averaged:** one slow frame (another program grabbing the CPU) would make an instant reading
jump from 7 to 2 and back, which looks like a bug. Averaging the last `FPS_WINDOW = 20` frames
shows the real throughput.

#### The snapshot contract, exactly

```python
{
  "ts": 31.5,                       # video seconds
  "source": "crowded.mp4",
  "fps": 8.2,                       # measured, moving average
  "total_people": 7,
  "peak_people": 9,
  "zones": [
    {"name": "Main Zone", "count": 7, "capacity": 4, "fill": 1.75,
     "status": "OVER", "over_for": 3.2, "avg_dwell": 12.0, "max_dwell": 24.0}
  ],
  "alerts_active": 1,
  "new_alert": None                 # or {"id":1,"zone":"Main Zone","keyframe":"/evidence/alert_1.jpg"}
}
```

**Why every number is cast to `int`/`float`:** numpy scalars are **not JSON-serialisable**. A raw
`np.int64(7)` reaching FastAPI's encoder raises `TypeError: Object of type int64 is not JSON
serializable`. Casting at the boundary means the snapshot is plain JSON all the way out.

**Why `fill` is guarded by `if capacity else 0.0`:** a zero capacity would divide by zero and take
the whole snapshot down.

#### `render(flags)` — why the toggles work without a restart

```python
"GET /video?boxes=1&zones=1&heat=0"
```

**Why flags rather than three separate renderers:** the browser can switch overlays on and off
mid-stream. No engine restart, no second model load, no dropped frames.

**Draw order is deliberate:** heat first (background), then boxes, then the zone polygons.

**Why:** heat is a *background layer*. Drawing it last would tint the box borders and the zone
outline, and a red box under a red heat blob becomes invisible.

**Why the zones are cached per clip:** `/video` renders up to 15 frames a second. Re-reading
`zones.json` for each one is 15 file reads a second for data that only changes when you run
`auto_zones.py`. The cache is keyed by clip name, so switching source never reuses another camera's
polygon.

## 6. `app/main.py` — FastAPI

### 6.1 `lifespan` — start once, stop cleanly

```python
db.init_db()
engine.start()
try:
    yield
finally:
    engine.join(timeout=2.0)
```

**Why lifespan and not a module-level `engine.start()`:** on import, `main.py` would spawn a thread
during a test run or a `--help`, and the model would download and load even when nobody asked. The
model must load **once per server process**, and must stop when the process stops.

**Why `init_db()` first:** the engine writes its first alert about **31 seconds** into the crowded
clip. On a fresh machine with no `results/` folder, that write would fail without the tables.

### 6.2 Routes

| Route | Purpose | Why it is built this way |
| --- | --- | --- |
| `GET /` | the dashboard page | `FileResponse`, because mounting `StaticFiles` at `/` would swallow `/api` |
| `GET /video` | MJPEG stream | `multipart/x-mixed-replace` plays in a bare `<img>` |
| `WS /ws` | push snapshots | steady beat, so the UI can show "0.5 s ago" |
| `GET /api/zones` | zones for a clip | defaults to the **playing** clip |
| `GET /api/alerts` | alert feed | `Query(50, ge=1, le=500)` bounds |
| `GET /api/history` | head-count chart | `oldest first`, ready to plot |
| `GET /api/sources` | clip allow-list | same function that guards switching |
| `POST /api/source` | switch clip | **400** for a name not on the list |

#### `/video` — the MJPEG stream

```python
def frames():
    delay = 1.0 / max(config.MJPEG_MAX_FPS, 1)
    try:
        while request.client is not None:
            jpeg = engine.render(boxes=..., zones_on=..., heat=...)
            yield (f"--{BOUNDARY}\r\nContent-Type: image/jpeg\r\n"
                   f"Content-Length: {len(jpeg)}\r\n\r\n").encode("ascii") + jpeg + b"\r\n"
            time.sleep(delay)
    finally:
        return
```

**Why a *sync* generator and not `async def`:** each frame is a small **blocking CPU job**
(drawing plus JPEG encoding). Starlette runs a sync generator in its **threadpool**, so it does not
block the event loop that also serves `/ws` and the API. An async generator would block that loop
and the dashboard's numbers would stutter while the video plays.

**Why `time.sleep(delay)`:** encoding is cheap, but there is no point sending faster than
`MJPEG_MAX_FPS = 15`. Without the cap the stream pushes the CPU to 100% for no visible gain.

**Why `try/finally`:** when the browser closes the tab, Starlette closes the generator, `finally`
runs, and the loop stops. That is exactly how a disconnecting client frees its CPU share.

**Why `multipart/x-mixed-replace`:** this is the pre-WebRTC trick that makes video work in a plain
`<img>` tag. The browser keeps the connection open and repaints each part.

#### `/ws` — the snapshot push

```python
await websocket.accept()
try:
    while True:
        _, _, snapshot = state.get()
        await websocket.send_json(snapshot)
        await asyncio.sleep(config.WS_INTERVAL)
except WebSocketDisconnect:
    return
```

**Why a steady beat rather than "send only on change":** the UI also needs to know that **nothing**
changed, so it can display "last update 0.5 s ago". A steady beat is simpler than diffing, and the
payload is only a few hundred bytes.

**Why catch `WebSocketDisconnect`:** closing a tab raises it, and that is normal. Without the catch
every tab close would print a traceback.

#### `POST /api/source` — the 400

```python
name = payload.get("name") if isinstance(payload, dict) else None
if not isinstance(name, str) or name not in list_clips():
    raise HTTPException(status_code=400, detail=f"Unknown source: {name!r}")
```

**Why read the body by hand:** the body is one optional field, and a hand-written check returns a
clear **400** instead of FastAPI's 422 for a name that simply does not exist.

**Why 400 and not 404:** the request is malformed (it names something that is not a valid source),
not a missing page. 400 tells the client *"fix your body"*.

## 7. `static/index.html` — deliberately bare

```html
<img src="/video" alt="live annotated video">
<pre id="snapshot">connecting...</pre>
```

**Why so plain:** P5 proves the **backend** works. The real dashboard with Tailwind and Chart.js
arrives in the next step, and adding a build step now would risk the "no build step" rule. This
page is the smallest client that proves the MJPEG stream and the WebSocket both work.

**Why the WebSocket URL is built from `location`:** `ws://` vs `wss://` must follow the page's own
protocol, or the connection is blocked as mixed content once the app is served over HTTPS.

## 8. `start.bat` — one double-click

```bat
cd /d "%~dp0"                       & rem work from this file's folder, whatever the shortcut says
if not exist ".venv\Scripts\python.exe" ( ... pause & exit /b 1 )
call ".venv\Scripts\activate.bat"
start "" cmd /c "timeout /t 4 >nul & start "" http://127.0.0.1:8000"
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

**Why `cd /d "%~dp0"`:** a Windows shortcut has its own "start in" folder. Without this line the
relative `.venv` path would resolve somewhere else and the script would fail confusingly.

**Why the venv check first:** a clear *"create it with `py -3.12 -m venv .venv`"* is far better than
`'uvicorn' is not recognized`.

**Why the browser opens after a 4-second delay:** `start` returns immediately, so opening it first
would show a "cannot connect" page. Four seconds is enough for YOLO to load on CPU.

**Why `--host 127.0.0.1`:** this is a demo on a laptop, not a public service. Binding only to
localhost means nothing on the network can reach it.

## 9. `scripts/smoke_test.py` — the end-to-end proof

**Why this file exists:** unit tests prove functions work in isolation. P5's failure mode is
different — *"the pieces are fine but the app does not start"*. Only a real uvicorn process catches
the lifespan, the thread, the static mounts, the MJPEG stream and the WebSocket handshake.

**Why it waits instead of sleeping:** `wait_for_server` polls `GET /` until it answers. A fixed
sleep is either flaky or slow, because model loading time varies.

**Why it refuses to run on a busy port:** a leftover server would make the test check **stale code**
and report a false pass.

**The ten checks, and what each one really proves:**

| # | Check | What it proves |
| --- | --- | --- |
| 1 | `GET /` → 200 + HTML | the static file is found and served |
| 2 | `GET /docs` → 200 | FastAPI itself mounted |
| 3 | `GET /api/zones` → list with keys | zones.json loads through the API |
| 4 | `GET /api/sources` → 3 clips | the allow-list works |
| 5 | `POST /api/source` bad name → **400** | **the security boundary** |
| 6 | `POST /api/source` good name → 200 | switching is wired |
| 7 | `GET /api/history` → list | DB read path works on an empty table |
| 8 | `GET /api/alerts` → list | DB read path works |
| 9 | `/ws` → all contract keys | the engine publishes a real snapshot |
| 10 | `/video` → MJPEG + JPEG bytes | rendering, encoding and streaming work |

**Why check 10 looks for `\xff\xd8`:** that is the JPEG "start of image" marker. Finding it proves
there is **real image data**, not just a header.

**Why the exit code matters:** a script that prints failures but exits `0` looks like a pass to any
automation — including a tired reader.

## 10. The live behaviour, measured

I let the server run on `crowded.mp4` until an alert fired, and read the API afterwards:

```
  [  10.2s] people= 4 zone=4/4 NEAR over_for=0.0s active=0 fps=8.5
  [  20.4s] people= 5 zone=5/4 OVER over_for=0.4s active=0 fps=8.7
  [  30.6s] people= 6 zone=6/4 OVER over_for=2.1s active=0 fps=8.2
  [  40.8s] people= 6 zone=6/4 OVER over_for=1.3s active=1 fps=8.4
  [  31.5s] NEW ALERT id=1 zone=Main Zone keyframe=/evidence/alert_1.jpg
```

```
--- /api/alerts ---
id=1 zone=Main Zone video_ts=31.5 peak=8 cap=4 ended=True keyframe=/evidence/alert_1.jpg

--- /api/history (last 10 min) ---
220 rows, zones ['ALL', 'Main Zone']
```

**What this proves, point by point:**

1. **`over_for` climbs** from 0.0 → 0.4 → 2.1 while the zone stays over — that is
   `AlertDebouncer.over_for` being read live through the API.
2. **`active` stays 0** until 3 seconds have passed, then becomes **1** — the debounce works.
3. **`video_ts = 31.5`** in the database matches the P4 demo exactly. Same rule, same result,
   now served over HTTP.
4. **`peak = 8`** while the firing count was 5 — the later rise from 5 to 8 was written by
   `update_peak`, proving the peak tracks the busiest moment, not the first moment.
5. **`keyframe`** points at a real file, and the photo shows `ALERT 1 31.5s` stamped on it.
6. **`220 head-count rows`** across zones `ALL` and `Main Zone`. Those are **2 video seconds**
   apart — measured as ~3.6 **wall** seconds, because processing runs at ~8 fps and one processed
   frame is 2 video frames. Video time is what the spec asks for, and it is the right unit: the
   chart describes the content, not the CPU speed.

**And the evidence photo itself** shows the crowd, the boxes, the red zone at `7/4`, and the
`ALERT 1 31.5s` stamp — the same frame the numbers came from.

- **`test_init_is_idempotent`** inserts an alert, calls `init_db()` again, and requires the row to

  must round-trip unchanged.
- **`test_frame_and_snapshot_always_match`** runs real threads and asserts the frame and snapshot
  always belong to the same instant. This is the test that would fail if someone split the lock.
- **`test_empty_state_is_safe_to_read`** pins the fix for the `KeyError: 'ts'` bug: the first
  snapshot must be valid, not `{}`.

**One test bug I hit and fixed:** `test_rows_come_back_oldest_first` first used a hard-coded
`2026-11-09T14:00:00` timestamp. `headcount_since(10)` filters against the **current** wall clock,
so by the time the test ran, those rows were 75 minutes old and were correctly excluded. The test
was wrong, not the code; it now builds timestamps relative to `now`.

## 12. Problems found and fixed during this step

These are worth telling the panel, because they are real engineering, not scripted successes.

### 12.1 The first WebSocket message broke the contract

**Symptom:** the end-to-end script crashed with `KeyError: 'ts'` on the very first message.

**Cause:** `SharedState.__init__` started with `self._snapshot = {}`. The browser connects instantly;
YOLO needs a second or two to load. So `/ws` sent `{}` for the first ~2 seconds.

**Fix:** a new `empty_snapshot(source)` helper, and `SharedState` now starts with it. The contract
holds from second zero and every client can render without a special case.

### 12.2 `zones.json` was re-read 15 times a second

**Symptom:** none visible — just wasted work.

**Cause:** `_zones_for_render` called `load_zones()` on every `render()`, and `/video` calls
`render()` up to `MJPEG_MAX_FPS` times a second.

**Fix:** a per-clip cache (`self._zones_cache`). Keyed by clip name, so switching source can never
draw the previous camera's polygon.

### 12.3 A database write on every frame while an alert was open

**Symptom:** none visible, but about 8 extra connections per second during exactly the busiest part
of the clip.

**Cause:** `db.update_peak(alert_id, count)` ran unconditionally each frame.

**Fix:** `peak_counts` tracks the highest count **in memory** and calls `update_peak` only when the
number actually rises. The DB peak still ends up at the true maximum (verified: `peak = 8`), with a
handful of writes instead of hundreds.

### 12.4 A stale timestamps bug in my own test

Covered in section 11 — the test, not the code, was wrong.

## 13. What could go wrong (and the fix)

| Symptom | Cause | Fix |
| --- | --- | --- |
| `database is locked` | a connection leaked, or a `journal` left behind | close the app; delete `results/crowd.db-journal` |
| Page loads, video is blank | engine still loading YOLO | wait 2–3 s and reload |
| Video plays but numbers never move | engine thread died | read the terminal; the `[engine] stopped on ...` line names the cause |
| `/ws` errors immediately | engine not started (imported the app directly) | run through uvicorn, not `python app/main.py` |
| `POST /api/source` always 400 | the file is not in `demo_videos/` | check `GET /api/sources` |
| Port 8000 already in use | a previous server is still running | close that window, or use `--port 8001` |
| `Address already in use` in the smoke test | a leftover process on 8011 | the script says so and exits 1 |
| Alerts never appear | clip too calm, or zones stale | check `/api/alerts`; re-run `auto_zones.py` |
| Evidence folder empty | no alert has fired yet | play `crowded.mp4` for ~35 s |
| Video plays double speed | writer fps not divided by `STRIDE` | see P4 §5.3 — already fixed |

## 14. Five questions a panel may ask (with short answers)

1. **Why a background thread instead of processing frames inside the request?**
   A frame takes ~140 ms. If a request waited for it, every page load would stall for that long and
   two viewers would queue behind each other. The thread produces continuously; requests only copy
   the newest result, which takes microseconds.

2. **Why is `SharedState` one lock and not one per field?**
   Because the video and the numbers must describe the **same instant**. Two locks allow a reader
   to receive a frame from 10.0 s and a snapshot from 10.5 s, and the boxes would not match the
   counts. The threaded test proves the pair stays consistent.

3. **Why a new SQLite connection for every call?**
   SQLite connection objects cannot cross threads, and this app writes from the engine thread while
   FastAPI threads read. Opening a local SQLite file costs ~50–100 µs against a 140 ms frame, so the
   simple, thread-safe choice is also effectively free.

4. **How do you stop a browser from reading arbitrary files through `/api/source`?**
   `set_source` accepts a name only if it is in `list_clips()`, which is built from
   `demo_videos/*.mp4` itself. So the only accepted values are bare file names that really exist. A
   path like `../../zones.json` is not in that list and gets a 400 — and the smoke test asserts it.

5. **Why does the video stream use a *sync* generator?**
   Each frame is a small blocking CPU job. Starlette runs sync generators in its threadpool, so the
   event loop stays free to serve `/ws` and the API. An `async def` generator would block that loop
   and make the numbers stutter while the video plays.

## 15. Numbers to remember

- Engine: **~8 fps** on CPU; snapshot every **0.5 s**; head-count rows every **2 video seconds**.
- `FPS_WINDOW = 20` frames for the moving average.
- MJPEG capped at **15 fps**, JPEG quality **80**.
- Alert: fires after **3 s** over capacity, clears after **5 s** at or under.
- Database: `alerts` + `headcount`, one **short-lived connection per call**, all queries
  **parameterised**.
- Snapshot keys: `ts, source, fps, total_people, peak_people, zones[], alerts_active, new_alert`;
  each zone: `name, count, capacity, fill, status, over_for, avg_dwell, max_dwell`.
- Measured live: alert at **video 31.5 s**, **peak 8** in a **capacity 4** zone, **220** head-count
  rows, evidence `alert_1.jpg`.
- Smoke test: **10/10**; unit tests: **54**.

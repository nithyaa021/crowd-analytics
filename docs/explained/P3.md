# Step P3 — Zones, counting and automatic zone setup (explained for a beginner)

This note explains every file and function written in step P3, in plain English, with a tiny
number example for every idea. Read it once, then explain it out loud in your own words.

---

## 1. What this step does, in six sentences

1. A **zone** is a polygon drawn on the floor of one camera view, with a name and a capacity.
2. `app/zones.py` answers four questions: *which zone is this foot in?*, *who is in each zone?*,
   *is that zone OK, NEAR or OVER?* and *how do I draw it?*
3. `zones.json` stores zones **per clip**, because each clip has a different camera angle.
4. `scripts/auto_zones.py` finds the zone for you: it watches where feet actually land, turns
   the busiest patch into a polygon of at most 8 corners, and picks a capacity that produces the
   alert behaviour that clip is supposed to demonstrate.
5. `scripts/demo_step3.py` writes a video with boxes, the zone, live counts and the colour for
   OK / NEAR / OVER, and prints every status change with the video time.
6. `scripts/ray_casting_demo.py` explains the point-in-polygon maths in pure Python, for
   learning only.

Nothing in `app/vision.py` changed. P1 still does exactly what it did before.

---

## 2. The `zones.json` format

```json
{
  "crowded.mp4": [
    {
      "name": "Main Zone",
      "capacity": 4,
      "polygon": [[284, 232], [300, 274], [352, 309], [346, 359],
                  [488, 359], [467, 329], [404, 334], [330, 235]]
    }
  ]
}
```

| Part | Meaning |
| --- | --- |
| top-level key | the **clip file name**, so zones never get used on the wrong camera view |
| `name` | the label the dashboard shows |
| `capacity` | how many people this area is comfortable holding |
| `polygon` | corners in order, as `[x, y]`, **in the resized frame** (`FRAME_WIDTH = 640` wide) |

**Why coordinates are in the resized frame:** YOLO sees a 640-wide frame, so foot points come
out in 640-wide pixels. If zones were stored in 1280-wide coordinates, every test would need a
conversion, and a forgotten conversion is a silent bug. Storing them the way they arrive means
the app can compare feet and polygons directly.

**Numeric example:** the crowded clip is 1280x720 on disk. A person at x = 568 in the resized
frame is at x = 1136 in the file, but we never compute that — both zones and feet stay at 640
wide.

## 3. `app/zones.py` — the whole file

### 3.1 `Zone` — the dataclass

```python
Zone(name="Main Zone", capacity=4, polygon=<array shape (8,1,2)>)
```

**Why `(N, 1, 2)` and not a list of pairs:** that is the exact layout `cv2.pointPolygonTest`,
`cv2.fillPoly` and `cv2.polylines` expect. Converting once, here, means no other file has to
remember the reshape — and a forgotten reshape makes OpenCV read points as garbage instead of
raising an error.

`Zone.points()` converts it back to plain `[(x, y), ...]` for JSON, because a numpy array
cannot be written to JSON and the nested shape would be stored as one-item lists.

**Numeric example:** `[[10, 10], [20, 10], [20, 20]]` becomes an array of shape `(3, 1, 2)`,
and `points()` turns it back into those three pairs.

### 3.2 `make_polygon(points)`

One job: turn readable pairs into the array OpenCV wants.

**Why it exists:** the same conversion happens when loading from JSON and when testing, so it
lives in one place instead of being copy-pasted with a different dtype somewhere.

### 3.3 `load_zones(path, source_name)`

Reads zones.json and returns the list of `Zone` objects for one clip.

Three failure modes are handled with a message a human can act on:

| Problem | What happens |
| --- | --- |
| File missing | `Zones file not found: <path>` |
| File is not valid JSON | `Zones file is not valid JSON: <path> (<reason>)` |
| Clip has no entry | `No zones for clip 'x.mp4'` + the exact command to fix it |

**Why the third one is an error instead of an empty list:** an empty list would draw nothing and
count zero people, and the demo would look "broken but calm". An error naming
`scripts/auto_zones.py` tells you the actual fix in one line.

An empty *file* is treated as `{}` rather than a JSON error, because that half-finished state
is common while learning.

**Numeric example:** loading `normal.mp4` from the file in section 2 gives a list with 1 zone,
capacity 4, polygon shape `(7, 1, 2)`.

### 3.4 `zone_of(zones, point)`

```python
inside = cv2.pointPolygonTest(zone.polygon, (float(x), float(y)), False)
if inside >= 0:
    return zone
```

**Why `>= 0`:** OpenCV returns `+1` for inside, `0` for exactly on the edge, and `-1` for
outside. Treating `0` as inside stops a person walking along a painted line from flickering in
and out of the count on alternate frames.

**Why `measureDist=False`:** we only need "in or out". Asking for the real distance is slower
and we would throw the number away.

**Why "first match wins":** polygons may overlap, and the rule must be predictable. Listing the
important zone first in `zones.json` is enough to control the answer.

**Numeric example:** zone = square 100..200. Point `(150, 150)` → `+1` → inside. Point
`(50, 50)` → `-1` → `None`. Point `(100, 150)` → `0` → inside.

### 3.5 `count_by_zone(zones, people)`

Returns `{zone name: [Person, Person, ...]}`.

**Why it starts with every zone set to an empty list:** the dashboard must be able to show
`Main Zone 0 / 4`. If empty zones were dropped from the dict, a zone that just emptied would
vanish from the screen instead of showing zero.

**Why people outside all zones are dropped:** they are not in any area we are responsible for.
Counting them in a zone would make that zone look fuller than it is.

**Numeric example:** two people, feet at `(150, 150)` (inside Main Zone) and `(600, 40)`
(outside everything) →

```python
{"Main Zone": [person1]}
```

### 3.6 `status_for(count, capacity)` — the one rule everything shares

```python
if count > capacity:            return "OVER"
if count >= NEAR_RATIO * capacity:  return "NEAR"
return "OK"
```

`NEAR_RATIO` is `0.8` in `app/config.py`, so it is a setting, not a magic number buried here.

| count | capacity | maths | status |
| --- | --- | --- | --- |
| 7 | 10 | 7 < 8 | OK |
| 8 | 10 | 8 >= 8 | NEAR |
| 10 | 10 | 10 > 10 is false | NEAR |
| 11 | 10 | 11 > 10 | OVER |

**Why "exactly full" is NEAR and not OVER:** the zone is not over its capacity yet. Only the
11th person makes it over. That is the edge case a panel loves to probe, and it is covered by a
test.

### 3.7 `draw_zones(frame, zones, counts)`

Draws, for each zone:

1. a **translucent fill** in green / amber / red,
2. an **outline** in the same colour,
3. a label like `Main Zone  6/5`.

**Why a copy of the frame:** the caller still needs the clean frame to detect on. Drawing on the
original would slowly paint boxes into the video that we then measure, frame after frame.

**Why translucent (25%):** a solid fill would hide the very people we are counting, and the
panel must be able to see both the colour and the crowd.

**Why the label sits above the topmost corner:** the label must not cover people. The top of a
zone is usually the far side of the floor, which is the emptiest part.

**Numeric example:** counting 6 people in a zone with capacity 5 calls `status_for(6, 5)` →
`OVER` → red, and the label reads `Main Zone  6/5`.

### 3.8 `_draw_label(...)`

A small helper that writes the text on a black strip, sized from `cv2.getTextSize`, so the text
stays readable over both a bright marble floor and a dark street.

### 3.9 `save_zones(path, source_name, zones)`

**Merges** the new entry into `zones.json` instead of rewriting the file, so generating zones
for the crowded clip cannot wipe the zones for the other two. Clip names are sorted so the file
order is stable and git diffs stay small.

**Why the custom formatter:** `json.dumps(indent=2)` puts every single coordinate on its own
line, so an 8-corner zone became 48 lines of bare numbers. This writes each `[x, y]` pair on one
line, which is reviewable on a projector.

## 4. `scripts/auto_zones.py` — how the zone is found

Run it with no arguments to do all clips, or name clips:

```powershell
.\.venv\Scripts\python.exe scripts\auto_zones.py
.\.venv\Scripts\python.exe scripts\auto_zones.py demo_videos\mid.mp4
```

### 4.1 Step 1 — `scan_clip`: one pass over the video

Runs the real `Detector` with `STRIDE = 2` and keeps the **foot point of every person in every
analysed frame**.

**Why remember the points instead of re-running detection:** detection is the slow part. One
pass gives both the density map and the per-frame counts, so the whole thing takes one video
scan instead of two.

**Numeric example:** a 674-frame crowded clip at `STRIDE = 2` → 337 analysed frames. If each of
those frames has about 8 people, we collect roughly 2,700 foot points.

### 4.2 Step 2 — `build_density`: dots become hills

Every foot point adds 1.0 to a heat image at that pixel, then a Gaussian blur spreads each dot
into a soft bump. Where people walk a lot, bumps overlap into a hill; a one-off passer-by stays
a faint mark.

**Why blur:** a zone made of single pixels would be a cloud of loose dots. Blur is what turns
"people were here" into "this is a floor area".

**The blur size was measured, not guessed.** Several values were tried on the real clips:

| blur fraction | kernel at 640 px | result on the crowded street |
| --- | --- | --- |
| 0.05 | 33 px | 7 separate islands; the biggest held ~2 people → useless tiny zone |
| 0.20 | 129 px | 1 island holding ~3,500 of 5,628 foot points → one real zone |
| 0.25 | 161 px | also 1 island, but the polygon spills over the pavement edge |

`DENSITY_BLUR_FRACTION = 0.20` is the value in the file, with that measurement written in a
comment next to it.

**Numeric example:** a spot where 50 people walked scores about 50 before blur; a corner where
2 people walked scores 2. After blur the 50 becomes a wide hill around 1.9 per pixel and the 2
disappears into the noise.

### 4.3 `largest_region`: threshold, then take the biggest patch

```python
mask = (heat >= peak * DENSITY_THRESHOLD).astype(np.uint8) * 255
```

With `DENSITY_THRESHOLD = 0.35`, only pixels at 35% of the strongest point survive. A small
morphological **close** (a 7x7 square) joins tiny gaps so one crowd becomes one region, then
`connectedComponentsWithStats` finds the patches and we keep the biggest.

**Why only the biggest:** that is the main walking area. Small side patches are doorways,
reflections or a couple of people passing, and including them would make the border look random.

**Numeric example:** peak density 1.9 → threshold 0.665. A pixel scoring 0.70 stays, a pixel
scoring 0.40 is dropped.

**Honest note:** this is why the crowded zone covers the near half of the street rather than
all of it. The far end has many small people, so after blur their density is lower than the
busy near end. The zone is a real busy area, not the whole picture — and the numbers in the
table prove it holds a crowd (peak 9, p90 7).

### 4.4 `simplify`: at most 8 corners

`cv2.approxPolyDP` replaces a wobbly stretch of border with one straight line. The tolerance
starts at 1% of the outline length and grows by a factor of 1.35 until the polygon has at most
`MAX_CORNERS = 8` points.

**Why 8:** a zone with 240 corners is impossible to explain and slow to draw. Eight corners is
enough to follow a real floor shape, few enough to describe out loud.

**Numeric example:** 240 contour points → 31 → 12 → 7 corners as the tolerance grows. The loop
stops at 7 because 7 ≤ 8.

There is also a guard: if the polygon collapses below 3 corners, the script stops and says so,
rather than saving a degenerate shape.

### 4.5 Step 3 — `count_inside`: polygon becomes numbers

For every analysed frame, count how many foot points pass
`cv2.pointPolygonTest(polygon, point, False) >= 0`. That gives one number per frame.

Then:

- **peak** = the busiest single frame,
- **p90** = the 90th percentile, i.e. the level the scene is at or below 90% of the time.

**Why p90 and not the average:** one quiet stretch drags an average down and makes a busy clip
look calm. p90 describes "how busy it gets when it is busy" without being ruined by a single
spike.

**Numeric example:** counts `[1,2,2,3,3,4,10]`. Sorted, the 90th percentile is about 6.4 → 6.
The average would be 3.6, which describes a much calmer scene than the clip really is.

### 4.6 Step 4 — `base_capacity`: the rule per role

| role | rule | why |
| --- | --- | --- |
| normal | `peak + 2` (min 3) | leave headroom, so the calm clip never alerts |
| mid | `round(0.9 * p90)` (min 3) | warn before it is full, so it sometimes goes NEAR |
| crowded | `round(0.6 * p90)` (min 3) | set it well below the typical level, so it goes OVER |

`MIN_CAPACITY = 3` stops a formula from producing a silly capacity like 1 for a quiet clip.

**Numeric example (the real numbers):**

```
normal : peak 2 -> 2 + 2 = 4
mid    : p90 6  -> round(5.4) = 5
crowded: p90 7  -> round(4.2) = 4
```

### 4.7 Step 5 — `tune_capacity`: check the promise, then adjust

Capacity is only right if the clip behaves as promised: **normal must raise 0 alerts, crowded
must raise at least 1.** So we simulate the alert rule and adjust by one person at a time if
needed.

```python
while adjustments < MAX_ADJUSTMENTS:
    if role == "normal" and alerts > 0:   capacity += 1
    elif role == "crowded" and alerts == 0:
        if capacity <= MIN_CAPACITY: break
        capacity -= 1
    else: break
    alerts = simulate_alerts(...)
```

**Why a safety stop:** a clip that simply cannot produce the wanted behaviour would otherwise
loop forever. `MAX_ADJUSTMENTS = 60` guarantees the script ends and reports.

**Why the adjustment is printed:** if a formula missed, you see
`capacity adjusted 6 -> 7 to get the expected alert behaviour`, so nobody has to guess why the
saved number differs from the formula. In our run all three clips matched their formula, so no
adjustment happened — and the column shows it.

### 4.8 `simulate_alerts`: the same rule as the engine, in 20 lines

```python
if count > capacity:
    over_seconds += seconds_per_sample
    under_seconds = 0.0
    if not alerting and over_seconds >= config.ON_DELAY:
        alerting = True; alerts += 1
else:
    under_seconds += seconds_per_sample
    over_seconds = 0.0
    if alerting and under_seconds >= config.OFF_DELAY:
        alerting = False
```

**Why simulate instead of just reading the peak:** a single over-capacity frame must not raise
an alert. The rule needs the zone to stay over for `ON_DELAY = 3.0` seconds, and to clear only
after `OFF_DELAY = 5.0` seconds. The simulation is what proves the capacity produces a *stable*
behaviour, not a flicker.

**Why use video time and not frame count:** `STRIDE = 2` means each analysed frame represents
2 source frames. At 30 fps that is `2 / 30 ≈ 0.067 s` per sample. Using frame counts instead
would make a 3-second delay fire after 3 samples (0.2 s), which is wrong.

**Numeric example 1:** capacity 5, one sample per 0.5 s, counts `6,6,6,6` → over for 2.0 s →
1 alert (fires at the 3.0 s mark only if the run continues that long).

**Numeric example 2:** counts `6,6,4,6,6` with ON_DELAY 3 s → the run never reaches 3 s
because the `4` resets the timer → **0 alerts**. That is the intended "don't cry wolf" behaviour.

### 4.9 Step 6 — save and prove

`save_previews` writes `outputs/zones_<clip>.png`: the first frame with the polygon, the
capacity and the peak drawn on it. **Why:** a polygon can be numerically perfect and visually
wrong. One picture settles it in a second.

`print_table` prints the summary the step asks for:

```
clip             role      corners capacity  peak  p90 alerts
--------------------------------------------------------------
crowded.mp4      crowded         8        4     9    7      1
mid.mp4          mid             8        5     8    6      0
normal.mp4       normal          7        4     2    2      0
```

`main()` finishes with a warning if a promise was not kept, so a mismatch is loud, not silent.

## 5. The real measured numbers

| clip | role | corners | capacity | peak | p90 | simulated alerts |
| --- | --- | --- | --- | --- | --- | --- |
| normal | normal | 7 | 4 | 2 | 2 | 0 |
| mid | mid | 8 | 5 | 8 | 6 | 0 |
| crowded | crowded | 8 | 4 | 9 | 7 | 1 |

**Check the promises:**

- normal: 0 alerts ✅ (peak 2, capacity 4 — two people of headroom)
- crowded: 1 alert ✅ (capacity 4, p90 7 — it is over most of the clip)

**An honest note about `mid`:** its rule gives capacity 5 and the tally is 0 simulated alerts,
because the zone is only over capacity for about a second at a time and `ON_DELAY` needs 3
seconds. The task only requires "normal = 0" and "crowded >= 1", so this is correct behaviour,
not a miss. It is also realistic: a busy escalator that spikes and recovers should not raise a
formal alert. If you want `mid` to alert, the honest lever is a lower capacity — and that is a
decision to make out loud, not to hide.

**Why the crowded peak (9) is lower than the P2 table's max (15):** different measurement.
P2 counted people in the **whole frame**; P3 counts only people **inside the zone**, which
covers the busy near half of the street. Both are correct for what they measure, and the zone
number is the one the alert uses.

## 6. `scripts/demo_step3.py` — the visible proof

```powershell
.\.venv\Scripts\python.exe scripts\demo_step3.py demo_videos\crowded.mp4
```

It writes `outputs/step3_crowded.mp4` and prints a line each time a zone's status changes:

```
    28.4s  Main Zone  4/4  OVER -> NEAR
    28.5s  Main Zone  5/4  NEAR -> OVER
    33.0s  Main Zone  4/4  OVER -> NEAR
```

### 6.1 `open_clip(path)`

Opens the file and reads its frame rate. **Why it matters here more than in P1:** every printed
line carries a video time, and a wrong fps would make the whole log wrong. Broken metadata falls
back to 25 fps with `DEFAULT_FPS`, and a NaN check stops a silent divide-by-zero.

### 6.2 `draw_people(frame, people)`

Green box plus a **red dot on the foot point**. **Why the dot:** it is the exact pixel the zone
test uses. Seeing the dots inside the polygon is the visual proof that counting is right — if a
box is inside but its dot is outside, the person correctly does not count.

### 6.3 `print_changes(previous, counts, zones, video_seconds)`

Compares this frame's status with the previous frame's and prints only the differences.

**Why only changes:** a 674-frame clip would print 337 near-identical lines. Only transitions
carry information, and they are exactly what you quote in the review.

**Why the first frame prints `start OK`:** it tells the viewer the baseline instead of
pretending nothing happened before the video started.

### 6.4 `total_text(counts)` and `draw_status_strip`

Top-left strip: `People 7 | Main Zone 7`. **Why the total as well:** it separates "the frame is
busy" from "the zone is full", which are different facts when people stand outside the zone.

### 6.5 `annotate(clip_path)` — the main loop

The same `grab()` / `retrieve()` stride pattern as P1, then: detect → `count_by_zone` → print
changes → draw people → draw zones → draw strip → write. The writer is created from the first
frame because `VideoWriter` needs the size up front.

## 7. `scripts/ray_casting_demo.py` — the maths, for learning only

This file is **not imported by the app**. It exists so you can answer "how does it know someone
is inside?" without hand-waving at OpenCV.

### 7.1 The idea

Stand at the point and shoot a laser to the right. Count how many edges it crosses:

- **odd** number of crossings → you started inside,
- **even** → you started outside.

**Numeric example:** point `(150, 150)`, square 100..200.

```
Edge (200,100)-(200,200): crossing at x = 200 > 150  -> flip -> inside (1)
Edge (100,100)-(100,200): crossing at x = 100 < 150  -> ignore
Horizontal edges: the ray runs along them            -> skip
1 flip = odd = INSIDE ✅
```

Point `(250, 150)`: no edge to the right → 0 flips = even = OUTSIDE ✅.

### 7.2 The subtlety this demo caught

On the first run, the pure ray-casting version said the point `(100, 150)` — exactly on the left
edge — was **outside**. That is wrong for our app, because OpenCV returns `0` there and
`zone_of` treats `0` as inside.

The fix is `on_segment()`, which checks the border explicitly before casting the ray, and the
crossing test is now strictly `>` instead of `>=`. After the fix:

```
5/5 cases agreed with the expectation.
```

And a cross-check against OpenCV on **20,000 random points**: `mismatches out of 20000: 0`.

**Why this matters on stage:** if the two disagreed, the zone edge would behave differently in
the demo and in the test, and nobody could trust either. This is why the file exists.

## 9. The three most important lines in this step

1. **`if inside >= 0: return zone`**
   `>=` is deliberate: on the edge counts as inside, so a person on the painted line does not
   flicker in and out of the count.

2. **`heat = cv2.GaussianBlur(heat, (kernel, kernel), 0)`**
   The blur is what turns scattered foot dots into a zone. Its size (0.20 of the width) was
   measured against the real clips, and a smaller one produced a 2-person zone that was useless.

3. **`if count > capacity: ... elif count >= NEAR_RATIO * capacity:`**
   Both thresholds matter, and exactly-full is NEAR. This one rule drives the colour, the label
   and the future alert, so it must be identical everywhere.

## 10. What could go wrong (and the fix)

| Symptom | Cause | Fix |
| --- | --- | --- |
| `No zones for clip 'x.mp4'` | zones.json has no entry for that file | Run `scripts\auto_zones.py demo_videos\x.mp4` |
| `No people were detected in this clip` | The clip is empty or the wrong file | Use a clip from `demo_videos/` |
| Zone is a tiny patch | Blur too small for a spread-out crowd | Raise `DENSITY_BLUR_FRACTION` |
| Zone covers the whole frame | Blur too large | Lower `DENSITY_BLUR_FRACTION` |
| `The zone collapsed to fewer than 3 corners` | Threshold picked noise only | Check the preview PNG, try another clip |
| Crowded clip reports no alert | Capacity too high, or zone too small | The script adjusts automatically; read the warning |
| Status flickers every frame | Raw counts jump by 1 near the boundary | Expected until P4 adds `ON_DELAY` / `OFF_DELAY` to the live path |
| `Cannot write video` | A player is holding the old MP4 | Close the player and re-run |

## 11. Five questions a panel may ask (with short answers)

1. **Why are zones stored per clip?**
   Each clip is a different camera angle, so a polygon in one picture means nothing in another.
   The key is the file name, which makes it impossible to use the wrong zone by accident.

2. **Why 8 corners?**
   Enough to follow a real floor shape, few enough to explain. The simplifier grows its
   tolerance until the polygon fits in 8 points, so the shape is always describable.

3. **Why is "exactly full" NEAR and not OVER?**
   Ten people in a zone that holds ten is at capacity, not over it. The eleventh person is the
   first one you can defend as an overflow, and `status_for` returns OVER only then.

4. **Why does the crowded zone cover only part of the street?**
   The far end is full of small, distant people; after blur their density is lower than the busy
   near end, so the threshold picks the near half. It is a real dense area — peak 9, p90 7 — and
   the alternative (a zone over the whole picture) would include empty pavement and understate
   the crowding.

5. **Why simulate alerts instead of trusting the formula?**
   A formula can produce a capacity that never trips, or trips on a single-frame fluke. The
   simulation applies the real `ON_DELAY` / `OFF_DELAY` rule, so the promise "normal never
   alerts, crowded does" is verified, not assumed.

## 12. Numbers to remember

- Zone storage: `zones.json`, keyed by **clip file name**, coordinates in the **640-wide** frame.
- At most **8 corners**; simplification starts at **1%** of the outline and grows by **1.35x**.
- Density threshold: **35%** of the peak; blur **0.20 × width** (129 px at 640 wide).
- `NEAR_RATIO = 0.8`, `ON_DELAY = 3.0 s`, `OFF_DELAY = 5.0 s`.
- Capacity rules: normal `peak + 2`, mid `0.9 × p90`, crowded `0.6 × p90`, never below **3**.
- Measured: normal **4 cap / peak 2 / 0 alerts**, mid **5 / 8 / 0**, crowded **4 / 9 / 1**.
- Ray-casting demo: **5/5** cases, and **0 mismatches** against OpenCV on 20,000 points.
- Tests: **17 total**, all passing.

# Step P1 — Detection and tracking (explained for a beginner)

This note explains every file and function written in step P1, in plain English, with a
tiny number example for each idea. Read it once, then explain it out loud in your own words.

---

## 1. What this step does, in five sentences

1. It turns the app from an empty skeleton into something that can **see people**: `app/vision.py`
   takes one video frame and returns a list of people, each with a box, a confidence and a
   tracking number.
2. **Detection** (YOLOv8 nano) answers "where are the people in *this* frame?".
3. **Tracking** (ByteTrack, which ships inside ultralytics) answers "which person from the
   previous frame is this?". It gives each person a stable `track_id`.
4. For every person we also compute the **foot point**, the bottom-centre of the box, because
   zones are drawn on the floor and feet stand on the floor.
5. `scripts/demo_step1.py` runs all of this over a whole video and saves an annotated MP4,
   so you can *watch* the result instead of trusting a number.

No zones, no counting, no web page yet. P1 is only: **frame in, tracked people out**.

---

## 2. New settings in `app/config.py`

| Name | Value | Why it is a setting |
| --- | --- | --- |
| `PERSON_CLASS_ID` | `0` | YOLO knows 80 classes; number 0 is `person`. Putting it in config avoids a bare `0` inside `vision.py` (our "no magic numbers" rule). |

One other package appeared: **`lap`**. ByteTrack needs a small maths solver called `lap` to
match detections between frames. It is not a new feature or a new choice of library — it is
a dependency that ultralytics installs itself the first time you track. We added it to
`requirements.txt` so a rebuild on another laptop is identical.

## 3. `app/vision.py` — the whole file

Think of this file as a small factory:

```
video frame  ->  Detector.track()  ->  [Person, Person, Person, ...]
```

Each `Person` is a plain Python object, not a YOLO tensor. That matters: the rest of the app
(analytics, JSON, database) should never need to know what a PyTorch tensor is.

### 3.1 `class Person` — the dataclass

A **dataclass** is a class whose only job is to hold data. Python writes the boring parts
(`__init__`, `__repr__`, equality) for us.

| Field | Type | Meaning | Example row |
| --- | --- | --- | --- |
| `track_id` | `int` | The tracker's stable number for this person | `7` |
| `box` | `tuple[int,int,int,int]` | `(x1, y1, x2, y2)` — top-left and bottom-right corners | `(100, 50, 140, 200)` |
| `conf` | `float` | How sure YOLO is, 0 to 1 | `0.90` |
| `foot` | `tuple[int,int]` | Bottom-centre point | `(120, 200)` |

Why a dataclass instead of a dictionary? Two reasons: dot access is readable
(`person.track_id` beats `person["track_id"]`), and a typo like `person.trak_id` fails
loudly instead of silently returning `None`.

Tiny example of the four fields for one person in one frame:

```python
Person(track_id=7, box=(100, 50, 140, 200), conf=0.90, foot=(120, 200))
```

### 3.2 `foot_point(box)` — two lines of geometry

```python
x1, _y1, x2, y2 = box
return (x1 + x2) // 2, y2
```

**Why it exists:** the middle of a box sits around a person's chest, which floats up and down
as they walk. The bottom-centre sits on the floor, where zones are drawn. Zones will test
this point, not the box centre.

**Numeric example** (the one in the test):

```
box = (100, 50, 140, 200)
x  = (100 + 140) // 2 = 240 // 2 = 120
y  = 200
foot = (120, 200)
```

`//` is integer division: `240 // 2 = 120`, and `241 // 2 = 120`, so we never get a half
pixel like `120.5`.

**What could go wrong:** if the box is tiny or upside-down (`y1 > y2`), the foot point is
still computed, but it will be in a strange place. YOLO always gives `y1 < y2`, so this is
not a real risk here.

### 3.3 `resize_frame(frame, width)` — same shape, smaller pixels

```python
new_height = round(height * width / old_width)
```

Why: the app fixes the frame width at 640 (config `FRAME_WIDTH`). Fixed width means drawing
coordinates, processing speed and the browser stream are predictable. Keeping the **aspect
ratio** means people do not look squashed.

**Numeric example 1 (shrinking):** a 1280x720 frame at width 640:

```
new_height = round(720 * 640 / 1280) = round(360.0) = 360
result shape = (360, 640, 3)
```

**Numeric example 2 (enlarging):** a 320x240 frame at width 640:

```
new_height = round(240 * 640 / 320) = round(480.0) = 480
result shape = (480, 640, 3)
```

**Why two interpolation modes?** `INTER_AREA` averages pixels, which looks clean when
shrinking. `INTER_LINEAR` blends neighbours, which is right when enlarging. Choosing the
wrong one is not fatal, just slightly blurrier.

**Fast path:** if the width already matches, the function returns the *same* frame object
(`return frame`). A test checks this with `assertIs`, which proves no wasteful copy happens.

### 3.4 `class Detector`

A thin wrapper around two things: the YOLO model and the ByteTrack tracker.

#### `__init__()`

```python
self.model = YOLO(config.MODEL_PATH)
```

**Why:** loading weights from disk takes about a second. Doing it per frame would make the
app 100x slower. We load once, then reuse.

#### `track(frame)`

```python
results = self.model.track(
    frame,
    persist=True,
    tracker="bytetrack.yaml",
    classes=[config.PERSON_CLASS_ID],
    conf=config.CONF,
    imgsz=config.IMGSZ,
    verbose=False,
)
```

Each argument, in plain words:

| Argument | Value | What it does |
| --- | --- | --- |
| `persist=True` | on | "Remember the tracker between calls", so IDs stay stable across frames |
| `tracker` | `bytetrack.yaml` | Use the ByteTrack tracker that ships with ultralytics |
| `classes=[0]` | person only | Ignore the other 79 classes (cars, bags, chairs) |
| `conf` | `0.35` | Drop detections the model is less than 35% sure about |
| `imgsz` | `640` | The size the model sees |
| `verbose` | `False` | Do not print YOLO's own log line for every frame |

**How ByteTrack works in two sentences:** it predicts where each person will be in the next
frame, then matches the new detections to those predictions. A detection that matches keeps
its old ID; an unmatched detection gets a new ID.

Then the important guard:

```python
if boxes.id is None:
    return []
```

**Why:** `boxes.id` exists only when the tracker ran. On an empty frame (or the very first
call in some cases) there are no IDs, and looping over `None` would crash. Returning `[]`
means "no people", which is true.

Finally, three parallel lists are zipped together. YOLO returns, for `N` people:

```
boxes.xyxy = [[100,50,140,200], [300,60,360,260], ...]   # N rows
boxes.id   = [7, 8, ...]                                  # N rows
boxes.conf = [0.90, 0.85, ...]                            # N rows
```

`zip` walks them in step, so row 1's box, ID and confidence stay together.

#### `_to_person(box, track_id, conf)` (staticmethod)

Converts one tensor row into a `Person`:

```python
x1, y1, x2, y2 = (int(value) for value in box.tolist())
```

**Why `tolist()` and `int()`:** YOLO returns PyTorch tensors. A tensor is not JSON-friendly
and prints like `tensor(100.)`. `int()` gives `100`, which draws and serialises cleanly.

**Why `float(conf)`:** the same reason — `float` turns a 1-element tensor into `0.9`.

#### `reset()`

```python
for tracker in getattr(predictor, "trackers", []):
    tracker.reset()
```

**Why:** ByteTrack numbers people 1, 2, 3 ... and keeps counting. If you play video A (ending
at ID 90) and then video B, the first person in B would be number 91, which is confusing.
`reset()` clears tracked, lost and removed tracks and restarts IDs at 1.

`getattr(..., "trackers", [])` is defensive: if the predictor has no `trackers` attribute yet
(no tracking has happened), the loop simply runs zero times instead of crashing.

## 4. `scripts/demo_step1.py` — the visible proof

Run it like this:

```powershell
.\.venv\Scripts\python.exe scripts\demo_step1.py demo_videos\your_clip.mp4
```

It writes `outputs\step1_<name>.mp4` and prints four numbers. There is **no window and no
`cv2.imshow`**, so it works on a laptop, in a terminal, or in a remote session.

### 4.1 `open_video(path)`

Opens the file and stops with `Cannot open video: ...` if OpenCV fails. **Why:** a clear
message beats a crash deep inside the loop.

### 4.2 `source_fps(capture)`

Reads the video's own frame rate so the saved clip plays at the same speed as the original.
Broken files can report `0` or `nan`; the function falls back to `DEFAULT_FPS = 25.0`.
**Numeric example:** a 15 fps input stays 15 fps; a file reporting `0` becomes 25 fps.

### 4.3 `make_writer(path, fps, width, height)`

Creates the MP4 writer with the `mp4v` codec, which OpenCV supports on Windows without
installing anything extra. **Why MP4:** you can double-click it in File Explorer.

### 4.4 `draw_person(frame, person)`

Draws three things:

1. the green box, using `person.box` — e.g. `(100,50)` to `(140,200)`;
2. the label `#7 0.90` (ID and confidence) just above the box — `max(y1 - 6, 12)` stops it
   from running off the top of the frame;
3. a filled red dot at `person.foot` — the point zones will later test.

### 4.5 `draw_status(frame, fps, people_count)`

Draws a black strip and white text in the top-left: `FPS 4.5 | People 4`.
**Why:** the panel can see at a glance that both detection and speed are real.

Running FPS is computed as:

```
running_fps = frames_processed / seconds_elapsed
```

**Numeric example:** after 10 processed frames in 2.0 seconds, the label shows `FPS 5.0`.

### 4.6 `annotate_video(video_path)` — the main loop

```python
if not capture.grab():
    break
if frame_index % config.STRIDE == 0:
    ok, frame = capture.retrieve()
    ...
frame_index += 1
```

This is the "skip frames cheaply" trick:

- `grab()` moves to the next frame **without decoding the picture**. It is the cheap part.
- `retrieve()` decodes the frame we just grabbed. It is the expensive part.
- With `STRIDE = 2`, we `retrieve()` only on frames 0, 2, 4, ... and `grab()`-only on 1, 3, 5, ...

**Numeric example** (the smoke test we ran):

```
Input video  : 45 frames at 15 fps
STRIDE       : 2
Processed    : frames 0,2,4,...,44  ->  23 frames
Skipped      : 22 frames (grab only, no decode, no YOLO)
```

Skipping halves the work and barely changes the numbers: a person is visible for many frames,
so analysing every second frame still catches them.

The writer is created from the **first resized frame**, because `VideoWriter` needs to know
the exact frame size before it can write. That is why `writer is None` is checked inside the
loop, not before it.

At the end: `capture.release()` and `writer.release()` close the files. **Why:** on Windows an
un-released MP4 can be truncated or locked.

### 4.7 `print_summary(...)`

Prints exactly the four facts the step asks for:

```
output       : C:\Users\akshaya\Downloads\crowd-analytics\outputs\step1_p1_clip.mp4
frames       : 23
avg FPS      : 4.5
avg people   : 4.00
unique IDs   : 4
```

**How `avg people` is computed:** total people seen across all processed frames, divided by
processed frames.

```
4 people x 23 frames = 92 person-appearances
92 / 23 = 4.00 people per frame
```

**`avg people` vs `unique IDs`:** in the smoke test they are both 4, but they measure
different things. If two people walk in and one leaves, you might see `avg people 1.50` while
`unique IDs 3`. Unique IDs is a count of *different* people; average people is a count of
*how crowded* each frame was.

### 4.8 `main()`

Checks that exactly one argument was given and that the file exists, then calls
`annotate_video`. **Why:** a friendly usage line beats an `IndexError` on `sys.argv[1]`.

## 6. The three most important lines in this step

1. **`model.track(frame, persist=True, tracker="bytetrack.yaml", classes=[0], ...)`**
   One call does detection *and* tracking. `persist=True` is what keeps a person's ID the
   same from frame to frame.

2. **`if boxes.id is None: return []`**
   The safety valve. Without it, an empty frame (or a first frame with no tracks) crashes the
   whole app.

3. **`new_height = round(height * width / old_width)`**
   The aspect-ratio formula. Miss it, and every person looks stretched like a funhouse mirror.

## 8. What could go wrong (and the fix)

| Symptom | Cause | Fix |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'lap'` | ByteTrack's solver was removed | `pip install lap`, or reinstall from `requirements.txt` |
| `Cannot open video` | Wrong path or unsupported codec | Check the path; try an MP4 (H.264) file |
| `Cannot write video` | `outputs/` missing or file locked | The script creates `outputs/`; close any player holding the old file |
| IDs restart at 1 mid-video | `Detector.reset()` was called | Only call `reset()` when switching videos |
| Very low FPS | CPU, `imgsz=640` | Expected; reduce `STRIDE` impact by keeping stride at 2 |

## 9. Five questions a panel may ask (with short answers)

1. **What is the difference between detection and tracking?**
   Detection finds people in one frame. Tracking links those detections across frames and
   gives each person a stable ID, so we can say "person 7 is still here" instead of "there is
   a person at (120,200) again".

2. **Why YOLOv8 nano?**
   It is the smallest YOLOv8 model: fast enough on a CPU and accurate enough for counting
   people at a distance. Bigger models are more accurate but far slower without a GPU.

3. **Why the foot point and not the box centre?**
   Because zones are floor areas. A person's centre moves up and down with their posture; the
   feet stay on the floor. Example: box centre `(120,125)` vs foot `(120,200)`.

4. **What does `conf=0.35` change?**
   It is a filter. At `0.35`, a detection at 0.30 is dropped and 0.90 is kept. Lower = more
   boxes (more false positives), higher = fewer boxes (more missed people).

5. **Why skip every second frame?**
   Halves CPU work for almost no accuracy loss, because a walking person appears in many
   consecutive frames. Example: a 45-frame clip becomes 23 tracked frames.

## 10. Numbers to remember

- Model: **YOLOv8 nano**, 80 classes, **class 0 = person**, weights `yolov8n.pt` (6.2 MB).
- Tracking: **ByteTrack**, `persist=True`, IDs restart at **1** after `reset()`.
- Frame width: **640**; stride: **2**; confidence: **0.35**; imgsz: **640**.
- Foot point formula: `((x1 + x2) // 2, y2)`.
- Smoke test: 45 source frames → **23 processed**, **4 people**, **4 unique IDs**, **4.5 FPS**.
- Tests: **8 total** (3 config + 5 vision), all passing.
